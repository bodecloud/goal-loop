OVERVIEW.TXT _ □ ×

What Goal Loop is

A small verifier-backed continuation loop.

Goal Loop gives Cursor and other coding agents a bounded working mode: write an objective to a project-local contract, run shell verification after each completed turn, continue only when verification fails, and stop only when verification passes or the loop aborts.

The key rule is simple: the agent does not decide when the work is done. The verifier does.

BOUNDARY.INI _ □ ×

Current product boundary

  • Primary command: /goal
  • State file: .cursor/goal/active.json
  • Verifier commands run in the shell
  • Failure returns followup_message
  • Success or limits stop the loop

v0.1.0 is not an agent platform, planner OS, dashboard, or orchestration stack. It is a narrow completion loop.

MODEL _ □ ×

What problem this solves

Problem 1: premature agent completion

Agents often stop when the work merely looks done. Goal Loop moves completion authority into a verifier command that can fail mechanically.

Problem 2: manual "continue" overhead

With Auto-run enabled, failed verification becomes the next instruction automatically, so the operator does not need to keep nudging the agent.

Problem 3: hidden runtime state

Goal Loop keeps state and logs in the project so every loop remains inspectable and portable.

SETUP _ □ ×

Install and workspace setup

1. Clone or install

git clone https://github.com/bodecloud/goal-loop.git
cd goal-loop
cursor-agent --plugin-dir "$PWD" --workspace /path/to/project

This repo proves the local plugin shape and CLI loading path. It does not itself prove current marketplace availability or the exact current Cursor IDE local-plugin UX.

2. Optional project defaults

{
  "verify": {
    "commands": ["npm run build"],
    "cwd": ".",
    "timeout_ms": 600000
  },
  "limits": {
    "max_iterations": 20,
    "max_wall_ms": 7200000
  }
}

Save that in .cursor/goal/defaults.json.

3. Auto-run matters

Goal Loop still verifies without Auto-run, but unattended continuation depends on Cursor Agent Auto-run being enabled.

USAGE _ □ ×

Shortest useful path

Start with one clear objective and one real verifier:

/goal "Fix build" --verify "npm run build"
  1. The command writes .cursor/goal/active.json.
  2. The agent works on the objective.
  3. The stop hook runs after a completed turn.
  4. The verifier runs in the shell.
  5. Failure returns a log-backed followup_message.
  6. Success marks the goal completed and returns {}.

Support commands

/plan [objective]
Draft the objective and verifier without activating the loop.
/goal-status
Inspect the active objective, iteration, verifier, and last log path.
/goal-abort
Abort the loop, preserving or removing state depending on intent.
ACTIVE.JSON _ □ ×

The runtime contract

Goal Loop is powered by one project-local JSON file. It is not just metadata; it is the state machine the command, hook, and agent all read. 

{
  "version": 1,
  "status": "active",
  "objective": "Fix the app build",
  "verify": {
    "commands": ["npm run build"],
    "cwd": ".",
    "timeout_ms": 600000
  },
  "limits": {
    "max_iterations": 20,
    "max_wall_ms": 7200000
  },
  "completion_promise": null,
  "started_at": "2026-06-30T00:00:00.000Z",
  "iteration": 0,
  "last_verify": null
}
Field Purpose
objective The human target the agent is working toward.
verify.commands Shell commands rerun after each completed turn.
verify.cwd Working directory used by verifier command execution.
limits Guardrails against runaway looping.
last_verify Latest verifier result, exit codes, and log path.
VERIFIER _ □ ×

Choosing a verifier that actually proves the request

Good verifier traits

  • Deterministic
  • Relevant to the user's real request
  • Cheap enough to rerun often
  • Strong enough to prove the intended outcome

Good fits

npm run build
npm test -- --testPathPattern=auth
scripts/smoke-check.sh
test -f generated/report.json

Bad fits

Lint for a runtime bug, file existence for a semantic rewrite, or a flaky network probe for a deterministic local fix. The loop will only be as honest as the verifier you choose.

LIMITS _ □ ×

Stop conditions and failure behavior

Success

When every verifier command exits cleanly, the hook marks the goal completed and returns {}.

Failure continuation

When verification fails, the hook writes a numbered run log, updates last_verify, and returns a followup_message containing a log tail.

Abort paths

Goals abort through /goal-abort, iteration limit exhaustion, or wall-clock limit exhaustion.

Fail-open hook errors

Unexpected hook errors write .cursor/goal/runs/hook-errors.log and return {} so a broken hook does not trap the agent.

TROUBLESHOOT _ □ ×

First places to inspect when behavior looks wrong

Check runtime state first

  • .cursor/goal/active.json
  • .cursor/goal/defaults.json
  • .cursor/goal/runs/
  • last_verify.log_path

If the loop stops after one failure

Check whether Cursor Agent Auto-run is enabled. Goal Loop can emit the continuation payload, but Cursor still needs to submit it.

If the verifier passes but the user is still unhappy

That usually means the verifier was too weak for the actual request, not that the loop disobeyed its contract.

CHECKLISTS _ □ ×

The compact runbook

Before starting a goal

Confirm the objective is bounded, the verifier matches the real request, and Auto-run is configured if unattended continuation is expected.

When a loop keeps failing

Inspect the active contract, defaults, numbered run logs, and hook-errors log before changing tactics. Repetition without inspection usually means the proof surface or scope is wrong.

When a verifier passes but feels wrong

Re-evaluate whether the verifier actually proved the user's request or only a narrow proxy such as build health or file existence.

REVIEW _ □ ×

Review the proof model, not just the outcome summary

Review the objective

Check that the active objective is bounded, aligned to the real ask, and not a vague catch-all that the verifier can never honestly prove.

Review the verifier

Ask whether the verifier actually proves the request, whether it is too broad or too weak, and whether it will produce actionable failure output.

Review success claims narrowly

A passing verifier proves only its own surface. Healthy review means matching the claimed success to that proof surface and not inflating it.

ADOPTION _ □ ×

Adopt it like a verifier discipline, not a magic autonomy switch

Start small

Begin with build repair, focused tests, or simple file-proof tasks. Do not start adoption with the flakiest or most subjective work in the repo.

Decide defaults deliberately

Commit .cursor/goal/defaults.json only when the repo truly has a shared baseline verifier. Otherwise prefer explicit --verify per goal.

Keep state treatment clear

Shared conventions belong in committed files. Live loop state and run logs belong in ignored files. That separation is part of the operating model.
